# The Agent Skills

The ten directories here are a **published, portable interface**. They follow
the open [Agent Skills](https://agentskills.io) specification and must keep
working when a user installs one of them, alone, into an agent that has never
heard of Issue Flow.

Everything about them — the catalogue, per-agent installation, the verified
compatibility matrix, the relationship with MCP and the CLI, and the rules a new
skill must follow — is in [`docs/skills.md`](../docs/skills.md). Read that
before changing anything here.

## The two invariants

**Nothing may reference anything outside its own skill directory.** Every real
client copies or scans only the directory holding the `SKILL.md`, so a `../`
link resolves in this repository and dangles wherever the skill is actually
used. The defect is invisible to the author and to the reviewer, and visible
only to the user.

A symlink is not the way around it. `vercel-labs/skills` fails the whole install
on any link entry in an archive, and git checks symlinks out as *"small plain
files that contain the link text"* wherever they are unsupported — on Windows,
the agent would read the path string as the contract.

**No generated file is committed here.** This directory holds sources; the tree
users install is assembled by `scripts/build-skills-tree.mjs` and published to
the `skills` branch by CI.

A reference cited by **one** skill lives in that skill, hand-written. Only when a
**second skill** cites the same text does it move to `_shared/contracts/`, and
the build materialises it into each consumer.

Nothing is listed by hand: the build derives what to materialise from the
`references/*.md` each `SKILL.md` actually cites. A shared contract nobody cites,
and a reference nothing points at, both fail validation.

```bash
just check     # validate the sources — what CI runs on every PR
just verify    # assemble the publishable tree and validate it strictly
```

`_shared/` has no `SKILL.md`, so it is not a skill and gets no install of its
own. It does not need one: every contract a skill reads is already inside that
skill.

`packages/issue-flow/prompts/_contracts/` is a build artifact too, generated by
`prebuild`/`pretest` and not versioned.

## What not to do here

- Do not commit a file carrying the generated banner. Nothing here should have
  one; `just check` fails on it. Edit `_shared/contracts/` instead.
- Do not promote a reference to `_shared/contracts/` until a second skill
  actually cites it. One consumer means one owner.
- Do not leave a reference the `SKILL.md` never cites. `skills:check` fails on
  it, and it was weight nobody read.
- Do not add a frontmatter field outside `name`, `description`, `license`,
  `compatibility` and `metadata` — `allowed-tools` included.
- Do not assume an orchestrator, a specific agent, or `CLAUDE.md` as a source of
  conventions. `AGENTS.md` is canonical; a vendor file is a pointer to follow.
- Do not restate in a `SKILL.md` what a contract already says.
