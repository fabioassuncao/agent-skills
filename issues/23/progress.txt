## Codebase Patterns
- Todo o código fica em `packages/issue-flow/` (monorepo). Rodar `npm run check` e `npm test` SEMPRE de dentro desse diretório, não da raiz.
- Testes ficam ao lado do código como `*.test.ts` (vitest `include: ['src/**/*.test.ts']`), nunca em um diretório `tests/`.
- Imports internos usam extensão `.js` (ESM + `moduleResolution: bundler`): `import { x } from './hash.js'`.
- Biome: aspas simples, `trailingCommas: all`, `lineWidth: 100`, indent 2 espaços, `useNodejsImportProtocol` obrigatório (`node:crypto`, não `crypto`).
- `tsconfig.json` exclui `**/*.test.ts` do typecheck; erros de tipo em testes só aparecem ao rodar `vitest`.
- Código e comentários em inglês; comunicação com o usuário e este log em pt-BR.
- Nunca usar caractere NUL literal em arquivo fonte — o arquivo vira binário para grep/git. Preferir payload canônico (JSON.stringify) quando precisar de separador inequívoco.
- Zod v4 é a versão em uso; `satisfies z.ZodType<T>` é o padrão do repo para manter schema e interface em sincronia (ver `sessionSnapshotSchema` em `src/schemas.ts`).
- Comandos git: rodar com `git -C <raiz-do-repo>` — o cwd do shell tende a ficar em `packages/issue-flow`.
- Não existe nenhum `CLAUDE.md` no repositório; os aprendizados moram só neste arquivo.
- Todo schema Zod novo com interface correspondente deve terminar em `satisfies z.ZodType<Interface>` (padrão de `sessionSnapshotSchema` e agora `issueMetadataSchema`).
- Estado global de módulo (ex.: o `Map` do registry de providers) precisa de um helper de reset exportado e chamado em `beforeEach`; vitest isola módulos por arquivo de teste, não por teste.
- `taskPlanSchema` é o contrato de arquivos já em disco: só afrouxar, nunca endurecer. `loadTaskPlan` faz `parse(...) as TaskPlan`, então defaults do Zod (ex.: `issueUrl` → `''`) chegam preenchidos aos consumidores.

- **Learnings for future iterations:**
  - O critério do PRD "um provider somente-leitura implementa apenas get/isAvailable" conflita com a assinatura listada, onde `create` é obrigatório. Seguimos a assinatura: `create` obrigatório, `close?` opcional; provider somente-leitura deve lançar em `create`. Se US-012/US-014 precisarem de um provider sem `create`, tornar `create` opcional exige ajustar todos os chamadores.
  - `registerProvider` sobrescreve a origem já registrada (last wins) — é o que permite trocar o provider real por um fake em teste (US-014).
  - `clearProviders()` existe só para isolamento de teste; use em `beforeEach` sempre que registrar providers, senão o estado vaza entre testes do mesmo arquivo (vitest isola módulos por arquivo, não por teste).
  - Vitest: `expect(x?.()).resolves` quebra quando o método opcional é `undefined` — envolver em `Promise.resolve(...)`.
  - O registry nasce vazio; nenhum provider se auto-registra ainda. US-004/US-005 precisam decidir onde chamar `registerProvider` (provavelmente um `src/issues/index.ts` de bootstrap importado pelos comandos) — hoje `getProvider('github')` lança "No Issue providers are registered".
