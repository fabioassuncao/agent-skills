## Codebase Patterns
- Todo o código fica em `packages/issue-flow/` (monorepo). Rodar `npm run check` e `npm test` SEMPRE de dentro desse diretório, não da raiz.
- Testes ficam ao lado do código como `*.test.ts` (vitest `include: ['src/**/*.test.ts']`), nunca em um diretório `tests/`.
- Imports internos usam extensão `.js` (ESM + `moduleResolution: bundler`): `import { x } from './hash.js'`.
- Biome: aspas simples, `trailingCommas: all`, `lineWidth: 100`, indent 2 espaços, `useNodejsImportProtocol` obrigatório (`node:crypto`, não `crypto`).
- `tsconfig.json` exclui `**/*.test.ts` do typecheck; erros de tipo em testes só aparecem ao rodar `vitest`.
- Código e comentários em inglês; comunicação com o usuário e este log em pt-BR.
- Nunca usar caractere NUL literal em arquivo fonte — o arquivo vira binário para grep/git. Preferir payload canônico (JSON.stringify) quando precisar de separador inequívoco.
- Zod v4 é a versão em uso; `satisfies z.ZodType<T>` é o padrão do repo para manter schema e interface em sincronia (ver `sessionSnapshotSchema` em `src/schemas.ts`).
- Comandos git: rodar com `git -C <raiz-do-repo>` — o cwd do shell tende a ficar em `packages/issue-flow`.
- Não existe nenhum `CLAUDE.md` no repositório; os aprendizados moram só neste arquivo.
- Todo schema Zod novo com interface correspondente deve terminar em `satisfies z.ZodType<Interface>` (padrão de `sessionSnapshotSchema` e agora `issueMetadataSchema`).
- Estado global de módulo (ex.: o `Map` do registry de providers) precisa de um helper de reset exportado e chamado em `beforeEach`; vitest isola módulos por arquivo de teste, não por teste.
- `taskPlanSchema` é o contrato de arquivos já em disco: só afrouxar, nunca endurecer. `loadTaskPlan` faz `parse(...) as TaskPlan`, então defaults do Zod (ex.: `issueUrl` → `''`) chegam preenchidos aos consumidores.
- Para código que executa binários externos, chamar sempre `run` de `src/utils/shell.ts` (nunca `execa` direto) — é o que permite `vi.mock('../../utils/shell.js', () => ({ run: vi.fn() }))` + `await import(...)` dinâmico, o padrão de teste de `src/utils/git.test.ts`.
- Ao classificar stderr de CLI externo, nunca usar regex genérica (`/not found/`): `gh: command not found` casaria com "issue inexistente" e transformaria ambiente quebrado em resultado vazio silencioso. Casar frases completas e específicas.
- Escrita atômica de qualquer artefato do pipeline: usar `writeFileAtomic` de `src/utils/fs.ts` (temp + rename + fallback EXDEV). Nunca chamar `writeFile` direto em arquivo que o pipeline recarrega.
- Provider/serviço que precisa do project root deve receber `projectRoot` opcional no construtor e cair em `getProjectRoot()` só quando não informado — é o que torna os testes com `mkdtemp` possíveis sem mockar git.
- Testes de provider baseado em arquivos usam `mkdtemp` real em `beforeEach` + `rm(..., { recursive: true, force: true })` em `afterEach`; só o shell (`run`) é mockado.
- Serviço que imprime para o usuário deve receber sinks injetáveis (`info`/`warn`, default `printInfo`/`printWarning`) — é o que permite asserção de mensagem em teste sem espionar o logger global.
- Nunca usar `rl.question` em loop: o readline descarta linhas que chegam entre duas perguntas (entrada pipada/typed-ahead se perde e o teste trava). Usar fila de eventos `'line'` + resolução em `'close'` (padrão `createLineReader` em `src/issues/resolver.ts`).
- Todo prompt interativo precisa de um caminho não-interativo determinístico: `interactive` injetável com default `process.stdin.isTTY && !CI`. Nada pode bloquear CI/headless.
- Erros de domínio que viram exit code do CLI usam classe própria com campo `exitCode` (`IssueResolutionError`), em vez de o chamador inventar o código.
- Em `applyPlaceholders`, espalhar os placeholders de conteúdo da Issue (`...issuePlaceholders(...)`) sempre por ÚLTIMO no objeto: valores injetados por último não são varridos de novo, então corpo de Issue nunca dispara substituição acidental.
- Teste de guarda contra shell-out precisa cobrir as duas formas de escrita: string literal (`'gh issue close'`) e argv (`execa('gh', ['issue', ...])`) — o código antigo usava a segunda.
- Comando de fase recebe `resolvedIssue?` como 2º parâmetro: `run.ts` resolve uma vez e propaga; uso avulso do subcomando resolve sozinho.
- Flag nova de CLI: mapeamento puro em `src/issues/cli-flags.ts` (testável) + helper de declaração (`withIssueOptions`) em `src/cli.ts`. Nunca colocar lógica em `cli.ts`, que roda `program.parse()` no import.
- Checagem de ambiente que pode virar opcional deve carregar uma chave estável (`CheckResult.key`), nunca ser filtrada pelo texto de `name` — o label é mensagem para o usuário e pode mudar.
- Smoke test de dependência externa ausente: `PATH=$TMPD` com symlinks só dos binários desejados (incluir `node`!) reproduz "gh não instalado" sem desinstalar nada.
- `printError`/`printWarning`/`printSuccess` saem todos por `console.log` (via `emit`), nunca por `console.error` — teste que captura mensagem de erro espiona `console.log`.
- Teste de comando que usa o registry de providers: `clearProviders()` + `registerProvider(fake)` no `beforeEach`. `ensureProvidersRegistered()` não sobrescreve o que já está registrado, então o fake sobrevive.
- Saída estruturada de agente headless usa tag XML-ish (`<issue-draft>`, `<issue-body>`), nunca JSON: o conteúdo é markdown multi-linha e um erro de escaping viraria falha total. Parsing sempre pela **última** ocorrência da tag (agente que mostra o formato antes de preencher).
