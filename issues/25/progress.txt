## Codebase Patterns
- Monorepo: o pacote é `packages/issue-flow/`. TODOS os comandos (`npm test`, `npx tsc --noEmit`, `npx biome check src/`) rodam a partir dele, não da raiz.
- Quality gate desta issue: `npx tsc --noEmit` + `npx biome check src/` + `npm test` (vitest, 29 arquivos / 407 testes na baseline da US-001).
- Não existe nenhum `CLAUDE.md` no repositório — aprendizados vão para este arquivo.
- Retrocompatibilidade de `tasks.json` é regra dura: todo campo novo de estado entra como `?: boolean` (padrão de `analyzeCompleted`), nunca obrigatório, senão planos já no disco quebram no Zod / passam a parecer inacabados.
- `PIPELINE_PHASES` é o conjunto **default** e não deve ganhar fases opt-in; fases opcionais vivem em um conjunto derivado (`PIPELINE_PHASES_WITH_PR_REVIEW`) e são injetadas via `activePhases` no construtor do `PipelineManager`, que nunca precisa ser alterado.
- Convenção de import: sempre `.js` nas extensões (`./pipeline.js`), mesmo em TS.
- Zod é v4 (`^4.3.6`). O padrão `satisfies z.ZodType<Interface>` só funciona em schemas **sem** `.default()` (o default torna o tipo de entrada divergente da saída) — em schemas com default, não use `satisfies`.
- Fontes de dados injetáveis seguem o padrão `GitStateSources` (`session-git.ts`): uma `interface` com métodos, um `const defaultSources` no módulo e `{ ...defaultSources, ...opts.sources }` na função — testes passam só o que exercitam, sem `vi.mock`.
- Prompt interativo: `interactive` default = `stdin.isTTY && stdout.isTTY && !CI`; `stdin`/`stdout`/`info`/`warn` sempre injetáveis (padrão de `issues/resolver.ts`). Nos testes, `PassThrough` para a resposta e um `Writable` sumidouro para o eco do readline.
- Prompts (`prompts/*.md`) são em inglês e carregáveis nos testes com `loadPrompt('<nome>')` sem nenhum mock. Quando um prompt tem contrato com um parser (headings, formato de item, bloco de resultado), fixe o contrato em teste extraindo os exemplos do próprio arquivo — desalinhamento aqui degrada em silêncio, nunca em erro.
- Erros de domínio carregam o exit code (`IssueResolutionError`, `PrDiscoveryError`) em vez de o chamador inventar um.
- Estado global de módulo em testes (`setGlobalTimeout`, `setVerbose`) precisa ser restaurado no `afterEach` — não há "unset" para o timeout; use `setGlobalTimeout(undefined as unknown as number)`.
- Implementação selecionável por configuração entra por um `Record<kind, factory>` + `createX(kind = default)` no próprio módulo (ex.: `createPrReviewPublisher`); o consumidor importa só a interface e a factory, nunca a classe concreta.
- `src/cli.ts` roda `program.parse()` no import e por isso é intestável: toda lógica de flag (mapeamento e validação de combinação) vive em `src/cli-options.ts` ou `src/issues/cli-flags.ts`, com o erro de domínio (`CliFlagError`/`IssueFlagError`) capturado na action → `printError` + `process.exit(1)`. Comandos são sempre `await import('./commands/x.js')` dentro da action (lazy loading).
- Commander camel-caseia flags com hífen (`--pr-review` → `opts.prReview`) e inverte as negadas (`--no-branch` → `opts.branch === false`). Quando um teste depende desse nome, feche o contrato parseando com um `Command` real em vez de assumir a chave.
- `vi.mock('x', () => ({ ... }))` com fábrica literal quebra quando o grafo de imports cresce (um novo import interno passa a exigir um export não listado). Para módulos com vários exports (`core/session-git.js`), use sempre o mock parcial com `importOriginal`.
- Resultado produzido dentro de uma closure (runner de fase) e lido depois no corpo da função: use uma "caixa" (`const box: { v: T | null } = { v: null }`), nunca `let x: T | null = null` — o TS mantém o narrowing `null` no ponto de leitura e acusa `type 'never'`.
- Tabelas de apresentação tipadas como `Record<string, string>` (ex.: `PHASE_LABELS`) não quebram o build quando falta uma entrada — degradam no fallback. Sempre que houver fallback silencioso, extraia a leitura para uma função exportada (`phaseLabel()`) e fixe-a em teste.
- Blocos de saída montados inline com `console.log` no comando (resumo final do `run`) migram para `src/ui/*.ts` como `buildXLines()` (array de strings, testável) + `printX()`; o teste compara o array, não captura stdout.
- Cada chave de `.issue-flow.json` tem seu próprio `loadXConfig()` em `src/config.ts`, todos com a mesma forma: `readXConfigFile()` (usa `readProjectConfigFile()` + `schema.partial().safeParse` e avisa `Ignoring "<chave>" key`), camadas mescladas `{ ...file, ...env, ...cli }` e um `safeParse` final que degrada para `schema.parse({})` com aviso. Chave nova = copiar esse trio, nunca tocar em `readProjectConfigFile`.
- Só crie `setXCliOverrides()` (estado global de módulo) quando existir de fato uma flag na CLI alimentando-o; sem flag, o layer `cli` entra por parâmetro em `options` e evita código morto.
- Há mudanças **não commitadas pré-existentes** no working tree (`getIssueDir`, `exitOnError` do listr2, testes de `git.ts`/`pipeline-renderer.ts`) que NÃO são da issue 25. Commitar sempre com `git add <arquivos específicos>`, nunca `git add -A`.
