# Issue input and artifact ownership

Read execution-options for invocation choices. Accept an explicit GitHub URL/number, a local issue file/directory, an arbitrary problem document or story/specification, complete content supplied by the user/caller, or a list of these. An explicit source wins. With only an identifier, run `node scripts/artifacts.mjs resolve <id> --json` and inspect its `paths.issueFile`; otherwise resolve the GitHub repository from the current remote. When both sources are supplied or known to differ, ask which source to use rather than silently switching. Local-only requests must not perform remote probes.

For a structured local issue (issue.md), the first non-empty line is the H1 title and the remaining text is the body. Metadata is optional when reading; if present, report malformed metadata instead of inventing values. Identifiers are single path segments: reject slash, backslash, dot/dot-dot, and non-positive numeric identifiers.

For an arbitrary document, use its actual contents without requiring an H1 or metadata. For inline input, use the supplied text. Distinguish a reference to missing content from a complete demand; ask for missing requirements rather than inventing them. Preserve the original document and source path. During resolve-issue, when durable artifacts are needed, write a local issue.md representation with a descriptive title, source reference and the supplied problem content; do not rewrite the source file. Standalone planning preserves this context in its requested PRD/plan without expanding its output boundary. Analysis/review alone must not create artifacts unless requested.

Reuse an explicit safe identifier, otherwise derive a descriptive lowercase hyphenated slug from the title. Resolve each candidate through the helper: reuse only when source identity and scope match; otherwise add the smallest available numeric suffix. Approved groups use a descriptive group- prefix and enumerate every input. Never allocate a fake GitHub number or overwrite an unrelated plan. Record the original URL (including repository), project-relative path, or inline content in the local issue/PRD so resumption does not depend on chat history. Local numeric IDs never establish a GitHub association. Multiple repositories' issue numbers must retain their repository identity and use distinct artifact IDs when they collide.

Resolve each item in a list independently, retaining its explicit source; then let resolve-issue decide execution units. Treat links and dependencies as context, not automatic authorization to implement more demands. When an identifier matches local and GitHub inputs whose ownership is ambiguous, clarify the origin. A request explicitly naming GitHub uses GitHub; a local/inline request does not probe the network merely to check for alternatives.

For GitHub input, use an available authenticated GitHub capability. A gh example is issue view <number> --repo <owner/repo> --json title,body,labels,comments,state,url. Fetch linked context only when relevant. Missing access is a retrieval failure, not an empty issue. If complete content was supplied, work from it and state any limits on remote verification.

CLI and Skills share one artifact layout. The helper selects `<workspace>/.issue-flow/issues/<id>/` only when `<workspace>/.issue-flow/issues/` already exists; otherwise it selects `~/.issue-flow/projects/<project-id>/issues/<id>/` (or `ISSUE_FLOW_HOME`). Run `prepare <id>` before the first write and `reconcile <id>` after changing tasks.json. Do not create the workspace override implicitly, copy between stores, or hardcode either path. Honor explicitly supplied artifact paths. Issue artifacts are operational state: never stage or commit them. Never overwrite a different issue/branch's work; archive only with authorization, to a fresh directory without overwriting an earlier archive.

Do not write CLI-owned runState, executions, locks or telemetry. Preserve unknown fields in an existing task plan when updating your owned fields; reconciliation promotes the portable projection without making the Skill owner of a CLI session.
