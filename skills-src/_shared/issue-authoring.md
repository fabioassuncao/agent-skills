# Issue authoring and duplicates

Read for GitHub or local issue creation. Inspect the actual repository stack and affected code before describing the problem. Match the user's requested language; otherwise match existing issues, then repository documentation. Avoid expanding a small request into unrelated architecture work.

Apply repository templates first. Without one, write a proportionate body covering context, problem, objective, scope/out of scope, acceptance criteria, dependencies, risks and references. Omit irrelevant detail. Distinguish a hypothesis, research question, epic and executable demand using the canonical fallback taxonomy only when the repository declares none. A record of an idea is not authorization to implement it.

For duplicates, compare intent, domain and proposed change. Search multiple targeted keyword combinations and relevant labels/areas on GitHub, including closed items. Locally inspect metadata and read bodies of plausible matches. A matching open item should be reported with any proposed additional context. Ask about ambiguous overlap; do not reopen or comment on a closed issue automatically. An unavailable search is not proof that there are no duplicates.

One issue should represent one coherent deliverable. When several independent deliverables are requested, present a concrete split and honor the user's choice. Do not enforce an arbitrary count of sections, files or acceptance criteria as proof of excessive scope.
